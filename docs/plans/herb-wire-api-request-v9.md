# **요청 요약**

Multi-AI Desk(aidesk.koreatimes.co.kr)는 Herb CMS에 수신된 통신사 기사 중 지금 관심이 몰리는 기사를 골라 담당자에게 추천하고, 담당자가 선정한 기사의 영문 초안을 만듭니다.

Herb 통신사 뉴스 화면(app/news/delivery)이 쓰는 API를 확인한 결과 필요한 기능 대부분이 herb-api에 이미 있습니다. 따라서 신규 개발 대신 **기존 API 재사용 + 서비스 토큰 발급 + 소규모 보완 2건**을 요청합니다.

- **1단계(읽기 전용, 신규 개발 0건):** 서비스 계정·토큰 발급과 기존 읽기 API 4종 사용 허가. 10월 16일 시작을 희망합니다.

- **1단계 보완(소규모 수정 2건, 권장):** 목록 응답에 updatedDt 추가, updatedDt 기준 조회 조건 추가. 없어도 1단계는 시작할 수 있습니다.

- **2단계(초안 저장):** 통신사 뉴스 화면의 "기사작성" 기능이 쓰는 기사 생성 API와 기사 메모 API 재사용. 권한 범위 설정만 필요합니다. 11월 15일 희망.

- 발행, 삭제, 다른 기사 수정 권한은 요청하지 않습니다. 아이템 최종 선정, 사실 확인, 사진 작업, 검수, 발행은 지금처럼 Herb CMS에서 사람이 합니다.

# **사용 목적과 업무 흐름**

4주간 MVP를 운영해 아이템 발굴부터 영문 초안 확보까지 걸리는 사람 투입 시간을 50% 이상 줄이는 것이 목표입니다. 처리량은 4주차 기준 하루 최대 10건입니다. AI 결과물은 초안이며, 발행 판단은 기자와 데스크가 합니다.

| **통신사 (Herb 코드)**                                           | **원문 언어** | **AI 처리**                |
|------------------------------------------------------------------|---------------|----------------------------|
| 연합뉴스 국문 (yna_ko), 한국일보 (hk)                            | 한국어        | 번역 → 스타일링 → 교열     |
| 연합뉴스 영문 (yna_en)                                           | 영어          | 스타일링 → 교열            |
| Reuters (RT), AP (ap), AFP (AF), DPA (DP), UPI (UP), SCMP (scmp) | 영어          | 리라이트 → 스타일링 → 교열 |

## **MVP 업무 흐름**

1.  Multi-AI Desk가 2분 간격으로 신규·변경된 통신사 기사를 조회합니다. (API 1, 2)

2.  스포츠 기록표·일정표, 보도자료(연합 RPR), 같은 통신사의 같은 제목 중복을 점수 계산에서 제외합니다. (Multi-AI Desk 내부 처리)

3.  남은 기사로 같은 사안을 묶고 인기 점수를 계산합니다. (Multi-AI Desk 내부 처리)

4.  최근 24시간 내 Korea Times가 이미 작성·발행한 사안은 추천에서 제외합니다. (API 3)

5.  점수 상위 20건을 담당자에게 추천하고, 담당자가 최대 10건을 선정합니다.

6.  선정된 기사를 AI가 번역·리라이트·스타일링·교열해 영문 초안을 만듭니다.

7.  1단계: 담당자가 초안을 Herb에 붙여넣습니다. 2단계: Herb에 초안 상태로 자동 저장합니다. (API 5)

8.  원문 정정·취소가 감지되면 해당 초안에 기사 메모로 경고를 남깁니다. (API 6)

9.  사진 작업, 데스크 검수, 발행은 Herb CMS에서 사람이 진행합니다.

10. 발행 여부, 최종본, 수정 이력을 조회해 초안 수정량과 발행 비율을 측정합니다. (API 3)

# **수정판·정정·취소 처리 방식**

수신 XML(deliveryXMLContents)을 확인한 결과, 통신사마다 판 처리 방식이 다릅니다. Herb 측 별도 개발은 필요 없으며, Multi-AI Desk가 아래와 같이 처리합니다.

| **통신사**                 | **수정판 수신 방식**                                              | **Multi-AI Desk 처리**                           |
|----------------------------|-------------------------------------------------------------------|--------------------------------------------------|
| 연합뉴스 국문·영문         | 같은 ContentID로 재전송, XML Header의 Action 값이 C(신규)·U(수정) | ContentID로 판 연결, Action으로 신규·수정 구분   |
| 한국일보, SCMP             | 같은 deliveryId 행이 갱신됨 (updatedDt 변경)                      | updatedDt 변화로 수정 감지                       |
| Reuters, AP, AFP, DPA, UPI | 판마다 새 ContentID, Action은 항상 C                              | 제목·본문 유사도로 같은 사안에 묶고 최신 판 사용 |

- **판 중복:** 관련 기사 건수는 통신사당 상한을 두어 한 통신사의 수정판이 점수를 부풀리지 않게 합니다.

- **초안 원문:** 사안 안에서 통신사별 가장 최근 판(취소된 기사 제외)을 사용합니다.

- **정정·취소 감지:** 연합뉴스는 Action 값(삭제 코드가 있다면 그 값 포함), 나머지는 제목 표기(\[수정\], (삭제), \<취소\>, KILL, CORRECTED 등)로 감지합니다.

- **대상 미확인 시:** "원문 미확인 취소·정정 공지"로 담당자에게 알리고, 해당 초안에 확인 필요 메모를 남깁니다.

- 참고: Herb 화면의 "수정기사·삭제기사" 필터는 한국일보 기사 제목에서 "(수정)"·"(삭제)"를 검색하는 방식으로 파악했습니다. 별도 상태 값이 있다면 알려주세요.

# **API별 상세**

## **1. 통신사 기사 목록·검색 — GET /api/delivery2**

**현재 지원 파라미터:** deliverySource, deliveryCategory, fromDate, toDate(분 단위), urgencyType, searchText, andSearchText, includeWord, excludeWord, searchTitleYn, page, size, sortValue(YD 최신순, YA 오래된순)

**현재 응답 필드:** deliveryId, deliverySource, deliveryArticleTitle, urgencyType, categoryList, deliveryYmd, page(number, size, totalElements, totalPages)

**보완 요청 2건 (권장, 1단계 시작 조건 아님)**

1.  목록 응답에 **updatedDt** 추가.

2.  **updatedFrom**(초 단위) 조회 조건과 updatedDt 오름차순 정렬 추가.

이유: 현재 조회 기준인 deliveryYmd는 수정 시 바뀌지 않는 경우가 있습니다. 예를 들어 SCMP 기사 scmp_3370461은 deliveryYmd가 10-11 17:30으로 그대로인 채 updatedDt만 10-12 01:55로 바뀌었습니다. deliveryYmd 기준 조회로는 이 수정을 놓칩니다. 또 최신순 + page 번호 방식은 조회 중 새 기사가 들어오면 페이지가 밀려 누락·중복이 생깁니다.

**보완 전 운영 방식 (Multi-AI Desk 측 처리)**

- 2분마다 최근 15분 구간을 sortValue=YA, size=500으로 조회하고 deliveryId로 중복을 제거합니다.

- 한국일보·SCMP의 같은 ID 갱신을 잡기 위해 1시간마다 최근 24시간 구간을 한 번 더 조회합니다.

**과거 관련 기사 검색:** 같은 API에 searchText, searchTitleYn=N(본문 포함)을 넣어 사용합니다. 별도 개발이 필요 없습니다.

## **2. 통신사 기사 상세 — GET /api/delivery/{deliveryId}**

현재 응답에 필요한 정보가 모두 있습니다. 신규 필드 개발은 요청하지 않습니다.

| **필요 정보**              | **현재 Herb 필드**                                           |
|----------------------------|--------------------------------------------------------------|
| id, agency, agency_item_id | deliveryId, deliverySource, XML의 ContentID(한국일보는 guid) |
| headline                   | deliveryArticleTitle                                         |
| body_text                  | deliveryPlainContents                                        |
| body_raw                   | deliveryXMLContents                                          |
| byline, dateline, keywords | XML의 Writer, Desk, Region, ClassCode (연합 기준)            |
| category                   | deliveryCategory, deliverySubCategory, deliveryTag           |
| priority                   | urgencyType (원본 등급은 XML의 Urgency)                      |
| received_at, updated_at    | createdDt, deliveryYmd, updatedDt                            |
| 수정 구분                  | XML Header의 Action (C·U 등)                                 |

- urgencyType은 Herb가 단순화한 값이라 통신사 간 기준이 다릅니다(DPA는 24시간 96건 전부 긴급). Multi-AI Desk는 XML의 원본 Urgency 값을 통신사별로 해석해 씁니다.

- 연합 보도자료(RPR)는 XML의 Desk(보도자료)와 Source(발신 기관)로 구분해 추천에서 제외합니다.

## **3. 자사 기사 조회 — /api/article, /api/article/history**

- 대상: Herb에서 작성된 Korea Times 기사(초안·발행 모두)

- 필요한 조회 조건: 기간(생성·수정·발행 시각), 상태, 섹션, 페이지

- 필요한 응답: articleId, 제목, 본문(최종본), 상태, 섹션, 작성자, 생성·발행·수정 시각, 원본 deliveryId(기사작성 기능으로 만든 경우)

- 수정 이력(/article/history)으로 AI 초안 대비 최종본 수정량을 측정합니다.

- 기존 API의 목록 조회 파라미터를 안내해 주세요.

## **4. 서비스 계정·토큰**

- Multi-AI Desk 전용 계정 1개 (테스트·운영 환경 각각)

- 1단계 권한: 1·2·3·7번 읽기

- 2단계 권한: 5·6번 쓰기 추가. 이 계정이 생성한 초안에 한해 메모 작성 가능하며, 발행·삭제·본문 수정 권한은 없어야 합니다.

- 현재 웹 화면은 사용자 로그인 세션의 Authorization 헤더를 씁니다. 서버 간 호출용으로 만료 주기가 긴 토큰 또는 재발급 절차를 안내해 주세요.

- 웹 화면이 읽기 전용 호스트(READ_API_URL)를 따로 쓰는 것으로 보입니다(추정). 폴링 호출은 읽기 전용 호스트로 보내겠습니다.

## **5. 기사 초안 생성 (2단계) — "기사작성" 기능 재사용**

통신사 기사 상세 화면의 "기사작성" 버튼이 통신사 기사를 원본으로 기사를 생성합니다. 같은 API를 서비스 계정이 호출하는 방식을 희망합니다.

| **필드**                    | **설명**                                         |
|-----------------------------|--------------------------------------------------|
| headline, subheadline, body | 초안 제목, 부제, 본문 (허용 HTML 태그 안내 요청) |
| section, keywords           | 섹션, 키워드                                     |
| assignee                    | 담당 기자 또는 데스크 (필수 여부 확인 요청)      |
| 원본 deliveryId             | 기사작성 기능이 이미 연결하는 방식 그대로 사용   |
| ai_generated                | AI 작성 초안 여부 표시 (가능 시)                 |
| external_id                 | 중복 저장 방지용 고유키 (가능 시)                |

- 상태는 draft로 고정되어야 하며, API로 발행 상태 변경은 불가해야 합니다.

- 응답: articleId, 편집 화면 URL

## **6. 초안 경고 메모 (2단계) — /api/articlememo 재사용**

- 초안 본문을 수정하지 않고 기존 기사 메모 기능으로 경고를 남깁니다. 초안 수정 권한이 필요 없어 권한 범위가 좁아집니다.

- 용도: 원문 정정·취소 감지, 미확인 사실, 고유명사 표기, 엠바고 등 검수자가 발행 전 확인할 사항.

## **7. 코드 조회 — 기존 API 사용**

- 통신사·카테고리 코드: /api/delivery/category2 (deliverySource 그룹 코드·이름 포함)

- 부서: /api/dept/all

- 섹션 코드와 담당자(user_id, 이름, 역할, 소속, 활성 여부) 목록은 조회 API가 있으면 그 API를, 없으면 엑셀 또는 JSON 파일로 1회 받겠습니다. 2단계에 assignee·section이 필수가 아니면 요청하지 않습니다.

| 1\. 목록 (증분)             | 2분 간격                                    | 720회                             |
| 1\. 목록 (24시간 재확인)    | 1시간 간격, 회당 약 10페이지                | 240회                             |
| 2\. 상세                    | 기록표·보도자료·중복 제목 제외 후 1건당 1회 | 약 3,100회 (전량 조회 시 4,700회) |
| 3\. 자사 기사               | 10분 간격 + 선정 기사 이력 조회             | 200회 이하                        |
| 5·6. 초안 생성·메모 (2단계) | 선정 기사 1건당 1~2회                       | 20회 이하                         |
| 합계                        |                                             | 약 4,300회 (최대 5,900회)         |

- 상세 조회 피크는 시간당 약 250회(분당 약 4회)입니다.

- size=1000 조회도 현재 응답되므로, 서버 보호를 위한 size 상한과 분당 호출 한도를 알려주시면 맞추겠습니다.
